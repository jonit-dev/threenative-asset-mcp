# PRD: Import uncooked UE5 static meshes (Megascans UE5-only packs)

Status: probe done, ready to build · Opened 2026-09-25 · Probed 2026-09-25

## Problem

Fab's Megascans UE5 packs ship uncooked editor packages. An example is Common Hazel
(`81bc7ba6-4686-4f94-9d2b-83eb1fdc4079`), whose only artifact is `MS_Hazel_UE51` for UE5.1–5.6.
`fab_import_asset` exports **0 of 135 packages** from it. The probe found two separate defects.

1. **Meshes: no decoder.** CUE4Parse's `UStaticMesh.Deserialize` returns before any editor data in an
   uncooked package. The converter sees only cooked `RenderData`, so it exits 134 with
   `No StaticMesh ... output was produced`.
2. **Textures: wrong colours.** Editor textures do convert: 41/41 real textures, with only the 28
   impostor atlases failing, as on UE4. But the embedded source PNG is written as-is, and two things
   go wrong:
   - **`TSF_BGRA8` sources come out with R and B swapped.** Measured on Hazel's Winter leaves,
     which should be brown: mean RGB (0.025, 0.048, 0.090). Swapped back, they read brown, and the
     bark reads brown-grey instead of blue.
   - **`TSF_RGBA16` sources are linear but land in an sRGB slot.** UE treats 16-bit sources as
     linear. Hazel's Summer leaf atlas measures (0.046, 0.059, 0.008); after linear→sRGB it measures
     (0.23, 0.26, 0.08). The same atlas from UE4.27 Hornbeam via UE Viewer measures
     (0.20, 0.23, 0.14).

   Defect 2 affects **every** UE5 editor texture the modern converter imports, not just Megascans.

## Probe findings (all on disk under the Hazel download)

- Package: UE4 522 / UE5 1008 (UE5.1). The name table holds `NaniteSettings`, `SourceModels`,
  `HiResSourceModel` and `StaticMeshDescriptionBulkData`.
- Geometry lives in the **package trailer**: `FPackageTrailer` v2, with 49-byte entries and every
  payload local. Each payload is an `FCompressedBuffer` (magic `b7756362`) using Oodle (method 3,
  Kraken, 256 KiB blocks). The converter's existing `DecompressEditorPayload` already decodes these;
  the texture path uses it today.
- One payload per source-model LOD, in LOD order. No separate HiRes payload was present.
  - `SM_CommonHazel_Sapling_01`: 4 payloads, 15,351 / 7,950 / 2,282 / 522 triangles.
  - `SM_CommonHazel_Field_01`: 7 payloads. LOD0 is 1,770,899 triangles (535 MB raw), stepping
    down to 15,462 at LOD5. Payload 6 is an 8-triangle impostor card whose slot is
    `MaterialInstanceDynamic_21`.
- Payload format: UE5 new-format `FMeshDescription`. It is fully specified by
  [`ue5-mesh-description-reference.py`](ue5-mesh-description-reference.py), which parses every
  probed payload **byte-exact** (11 payloads, 4.7 KB to 535 MB). Attributes present:
  - `Vertices.Position ` (with a trailing space)
  - `VertexInstances.{VertexIndex, TextureCoordinate[4], Normal, Tangent, BinormalSign, Color}`
  - `Triangles.{VertexInstanceIndex (extent 3), PolygonGroupIndex}`
  - `PolygonGroups.ImportedMaterialSlotName` (e.g. `TwoSided`, `Tileable`)
- Conversion to glTF, verified by rendering Hazel Sapling_01 LOD0: a correct 1 m multi-stem shrub,
  with 96% of the bark normals facing outward.
  - Position becomes `(x, z, y) × 0.01`; normals map the same way without the scale.
  - **Keep UE's triangle order.** The Y/Z swap and UE's left-handedness cancel out. Flipping the
    winding made 0 of 15,351 faces agree with their stored normals.
  - Normals are stored (flags 34 = AutoGenerated|Mandatory) and non-zero, so they can be used as-is.

## Build

1. **Texture colour fix (≈1 h, ship first).** In `ThreeNativeConverter`, read `TSF_*` per editor
   texture. Swap R and B for `BGRA8`. For `RGBA16`, convert linear→sRGB when the texture feeds
   base colour; leave it linear for data maps (normal, mask). Regression test: a synthetic BGRA8 and
   RGBA16 source, checking pixels.
2. **Mesh decoder (≈1 day).** Port the reference parser to C# inside `ThreeNativeConverter`:
   - Trigger on `UStaticMesh` with `bCooked == false` and no `RenderData`.
   - Walk that package's trailer, decompress each payload, and parse it as `FMeshDescription`.
   - Take the payload with the most triangles as LOD0 and ignore payloads with fewer than 16
     triangles (impostor cards). Map triangles to material slots through `ImportedMaterialSlotName`
     against `StaticMaterials[].MaterialSlotName`.
   - Emit a GLB through the same material path as cooked meshes.
   - Unit test: a checked-in 4.7 KB payload (`SM_CommonHazel_Field_01` payload 6) parsed to known
     counts.
3. **Verify (≈2 h).** Add a real-pack test gated on the Hazel download. Render contact sheets and
   compare them against the Fab listing images, not just counts.

## Open decision

LOD0 of a Megascans UE5 tree is up to 1.77M triangles (UE4.27 Hornbeam's is 1.46M through the
existing path). **Default: import LOD0**, matching the UE4 route. Add a `maxTriangles` option that
picks the first LOD under the budget only if a game needs it.

## Still unknown

- Why Hazel's leaves still render darker than Hornbeam's after the colour fix. The atlases match in
  magnitude, so the likely cause is the Megascans foliage material's brightness and translucency
  parameters. Judge this in step 3 against the listing images.
- Sparse element arrays with holes. Every probed payload was fully allocated; compact by the bit
  array if one isn't.

## Out of scope

Impostor atlases (`T_Impostor_*`, and payload 6's billboard card). UE Viewer also produces no PNG
for them on UE4.27.
